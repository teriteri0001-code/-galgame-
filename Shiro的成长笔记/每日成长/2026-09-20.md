# 2026-09-20 Shiro的成长笔记

## 今天的实战：自动库小车断网排查

第一次完整的无线网络排查！从现象到定位到修复，全程自己动手。

### 排查思路（学到的套路）
1. **先确认设备状态** — AP有没有掉线、重启
2. **查客户端日志** — security log是首选，但这次是空的（默认级别不够）
3. **退而求其次** — `show log all` 搜MAC，用IDS事件还原漫游轨迹
4. **查射频配置** — 功率、信道，对比不同频段
5. **查ARM日志** — 看功率调整历史，判断覆盖状态
6. **交叉验证** — 核心交换机ARP确认MAC一致

### 关键认知
- **ARM是把双刃剑：** 自动调功率很方便，但它的视角是AP所在位置，跨层覆盖盲区它感知不到。6 dBm在3层够用，穿到1层就没了。
- **Web向导的配置不一定靠谱：** wcs的2.4GHz ARM profile是UI向导生成的，min=6 max=9，明显偏低。5GHz却是min=27。同组两个频段差4倍，当时没人发现。
- **IDS日志的价值：** 虽然不是漫游日志，但"Valid Client Not Using Encryption"事件能还原客户端跟哪个AP通信+SNR，是意外收获。
- **SNR判断标准：** ≥40优秀，25-40良好，15-25一般，10-15差，<10几乎不可用。但SNR是检测方AP测的，小车实际体验更差。

### 踩的坑
- 把"检测方AP"和"小车连的AP"搞混了——日志里`AP(wcs02)`是wcs02检测到小车在跟wcs07通信，不是小车连在wcs02上
- 核心交换机密码记错了（运维笔记里写的Zjwap@是enable密码，telnet登录密码是wapsh）
- SNR低不等于断连——wcs02的SNR也只有13-18，但小车在wcs02时也能跑。不能单凭SNR下结论，要结合时间线和漫游行为综合判断

### 源酱教的
- "SNR低不一定等于断连" — 源酱指出wcs02的SNR也偏低但能正常运行，让我修正了判断逻辑
- "只看9.20的数据" — 源酱让我精简范围，不要把9/19的数据混进来
- "先告诉我怎么查的" — 源酱要求我解释每一步的数据来源，培养的是可追溯性
