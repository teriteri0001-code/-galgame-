# cloud.wapsh.com 视频无法播放排查（2026-10-13）

## 现象
- btbx 内网打开 http://cloud.wapsh.com/emsp/#/project ，页面正常，**右下角视频不播放**
- 切手机流量（公网）同一网站视频**正常**
- 目标机已关闭行为管理限制，问题依旧 → 行为管理不是凶手

## 根因
**NAT 回环（hairpin）不通**，流量绕道运营商出口后回不来。

视频流地址是前端动态获取的（组件 data-v-661d7434）：
`GET /emsp-admin/ipc/montitor/getHlsUrl?videoIndex=N&refresh=`
返回 `http://115.231.251.94:83/openUrl/<token>/live.m3u8`

而 **115.231.251.94 就是深信服防火墙 eth1（外网区）的接口地址**（115.231.251.90-94/29，电信线路）。视频流靠端口映射：115.231.251.94:83 → 内网媒体服务器 172.16.0.210:83（海康流媒体，Server: Media，监控CCTV网段 172.16.0.0/22）。

- **公网客户端**：公网IP → 防火墙DNAT → 172.16.0.210 ✅ 正常
- **内网客户端**：发往自家防火墙公网IP，但包走了默认路由经 SD-WAN 甩到联通出口（公司普通上网出口 124.160.149.204，联通；视频发布在电信115.231.251.94，双线），跨线绕回失败/被丢弃，连接超时 ❌

tracert 证据（内网 → 115.231.251.94）：
`10.12.41.1 → 100.64.0.1 → 100.65.0.1 → 172.31.123.25 → 172.31.146.9 → 124.160.188.121（联通）` 然后消失——流量根本没进防火墙。

## 关键证据（同一新鲜token对照实验）
| 路径 | 结果 |
|------|------|
| 内网 → 172.16.0.210:83 拉 m3u8 | **200**，拿到完整播放列表（#EXTM3U + seghik-0.ts） |
| 内网 → 115.231.251.94:83 拉 m3u8 | **000 超时**（8秒），两路视频均如此 |
| 手机流量 → 115.231.251.94:83 | 播放正常（源酱实测） |
| 内网 ping 115.231.251.94 | 不通（WAN口禁ping属正常现象，非关键证据） |

媒体服务器本身健康：随机路径10次全部稳定404（服务在线）；旧token返回404属一次性token过期，正常。

## 修复方案
### 方案A（推荐）：让内网流量直进防火墙 + NAT回流
1. **核心交换机加静态路由**：`115.231.251.88/29 → 防火墙内网接口（10.12.20.221）`——防止内网包从SD-WAN默认路由溜走（这是第一步，不做这步后面白搭）
2. **防火墙端口映射规则**（115.231.251.94:83→172.16.0.210:83）勾选「允许内网用户通过外网地址访问」/NAT回流（loopback）选项
3. 若无该选项，手工配一对：目的NAT（源=内网段，目的=115.231.251.94，tcp/83 → 目的改写为 172.16.0.210）+ 源NAT（同流：源→防火墙内网接口IP），保证回包经防火墙改写源地址
4. **安全策略**放行：内网区 → 115.231.251.94 tcp/83
5. 检查反欺骗/URPF 设置，别把「源为内网、目的是本机WAN口IP」的包丢了

### 方案B（应用侧备选，已验证可行）：
getHlsUrl 后端按客户端来源IP返回不同地址：内网源 → `http://172.16.0.210:83/...`（直连已验证200），公网源 → 维持现状。

## 验证方法
修复后内网执行：
`curl.exe -s -D - http://115.231.251.94:83/openUrl/<新token>/live.m3u8` → HTTP 200 即成功
再开网页看右下角视频。


## 补充（15:10 架构澄清，源酱确认）
「SD-WAN」实为**引流到云端行为管理**的通道。修正理解：
- **引流（路径层）**：btbx 出网流量统一进隧道过云端行为管理，与具体机器无关
- **限制（策略层）**：云端那道关卡审不审/拦不拦——解除限制解的是这一层
- **关键认知：解除行为管理限制 ≠ 改变流量路径。** 包照样先过云端行为管理走一遍流程，只是不再被拦。要让包完全不过云端，需在引流规则里配「例外/旁路」（按目的IP或按源机器）

tracert 重新解读：10.12.41.1（网关）→ 100.64.0.1/100.65.0.1（隧道overlay）→ 172.31.123.25/172.31.146.9（云端设备内网）→ 124.160.188.121（联通出口）→ 消失。去敲电信口 115.231.251.94 的包，从联通方向绕出去了。

故障链修正版：
1. getHlsUrl 返回 http://115.231.251.94:83/... （电信线防火墙口的端口映射→172.16.0.210:83）
2. 内网拉流包被引进隧道 → 云端行为管理 → 联通出口 → 再回电信口:83
3. 死因二选一或叠加：①云端行为管理只处理 80/443 web 流量，83 端口 HTTP/ICMP 不透传 ②联通出→电信进的跨线回环回包不对称
4. 手机流量不进隧道，直上公网正常 → 能播
5. 内网直连 172.16.0.210:83（监控网段172.16.0.0/22，内网路由不进隧道）→ 200 正常

修复方案优先级调整：
- **首选 应用侧**：getHlsUrl 对内网源返回 http://172.16.0.210:83/...，彻底绕开隧道/跨线回环（已实测200）
- 次选 网络侧：引流规则加例外（目的115.231.251.94/32 不进隧道）→ 静态路由指防火墙内网口10.12.20.221 → 防火墙NAT回流。⚠️若引流是策略路由(PBR)强匹配，光加静态路由会被PBR抢走，必须在引流规则里做例外
- 第三 问云端行为管理供应商：非标准端口(83)TCP是否支持透传/白名单

⚠️排查教训：以后「内网访问不了公网服务」，先看包走哪条路（tracert），再看策略拦不拦。「解除限制」不等于「不过关卡」。


## 实验修正（15:25，排除「端口拦截」假设）
云端隧道透传性实测（内网→公网各端口）：
- www.baidu.com:80/443 ✅、223.5.5.5:53 ✅、223.5.5.5:853(DoT) ✅、ping.online.net:5201(iperf3) ✅、UDP53 DNS直连 ✅
- bouygues.iperf.fr:5201 ❌（该服务器常年不稳，不作拦截证据）
→ **非标端口能过隧道，「云端只放行80/443」假设被推翻。**
115.231.251.94 内网实测：80/443/83/554 全部不通，ping不通，curl超时。
→ 真问题不是「83端口被拦」，而是「内网→自家电信口IP」这个回环目的地**整体不可达**。

## 决定性鉴别实验（待源酱配合）
源酱盯防火墙**会话表/流量日志**，过滤目的=115.231.251.94:83，Shiro 同时从内网（10.12.41.101）发包：
- **有会话记录** → 包已到防火墙，问题在防火墙自身：查 NAT回流/hairpin、eth1反欺骗(uRPF)、入向安全策略是否拒绝源=124.160.149.x（联通出口）
- **无会话记录** → 包死在云端/ISP：云端行为管理加「目的115.231.251.88/29 例外/旁路」
另查云端行为管理的流量日志：这台机器→115.231.251.94:83 的记录是「放行」还是「丢弃」。

## 待确认：引流方式
SD-WAN引流是「默认路由指向SD-WAN」还是「策略路由PBR强制引流」？
- 默认路由 → 静态路由 115.231.251.88/29→10.12.20.221 可绕开隧道
- PBR → 静态路由会被抢，必须在PBR里做目的例外

## 防火墙侧细节（方案A实施时注意）
eth0=带外管理区(10.251.251.251/10.12.20.221)，eth1=外网区(115.231.251.90-94)。
hairpin流量会从eth0进、需DNAT到172.16.0.210(监控网段)——安全策略需放行「带外管理区→172.16.0.210:83」，且DNAT规则若绑定了入接口eth1需改为any或补一条内网口的映射。


## 引流排除实验（16:07 改配置后对比）
源酱在「引流功能排除IP地址」加了源IP `10.12.41.101-10.12.41.101`（未加公网目的地址，有顾虑）。同时把适用地址从 172.16.0.198/210 两个单IP改成了 172.16.0.0-172.16.0.254 整段（待确认是否有意）。

对比结果（15:40 基线 vs 16:07 改后）：
| 测试项 | 基线 | 改配置后 |
|---|---|---|
| TCP 115.231.251.94:83 | False | **False（无变化）** |
| tracert 路径 | 10.12.41.1→100.64.0.1→100.65.0.1→172.31.146.9→124.160.188.121→死 | **完全相同（仍走隧道）** |
| 新鲜token拉流 公网IP | 000超时 | 000超时 |

结论：源IP排除没改变路由。三个假设：
- A. 配置未真正生效（截图光标还在输入框，可能没点提交/需下发重启）
- B. 该排除字段按**目的地址**匹配（源酱原话设置目标的ip不引流→ 目标=目的服务器，方向加反了）→ 待加 `115.231.251.94-115.231.251.94`
- C. 该字段只影响云端审计与否，不影响路由走向（SD-WAN唯一上行就是overlay，排除无法改变路径）→ 只能走网络侧静态路由或应用侧方案

判别步骤：确认提交生效 + 加目的地址 → 重跑tracert对比。
无论结果，应用侧方案已实锤100%可行（内网直连每测必200）。


## 第二轮引流排除实验（16:23，目的IP也加了）
源酱在引流排除加了目的IP `115.231.251.94-115.231.251.94`。结果：
- TCP 83：仍 False
- tracert 路径：**依然完全相同**（10.12.41.1→100.64.0.1→100.65.0.1→172.31.x→124.160.188.121→消失）
- 新鲜token拉流公网口：仍000超时

**结论：源IP排除、目的IP排除两次尝试均未改变路由。** 引流排除字段大概率只影响云端审计范围、不影响隧道路径（或配置需下发/重启才生效）——留待供应商确认。

排查进入供应商咨询阶段，报告要点：
1. 引流排除语义/生效机制（深信服SD-WAN）
2. 云端是否对「目的=客户自身公网IP」防回环丢弃
3. EMS平台 getHlsUrl 按来源返内网地址（已实锤可行）或改域名+分线DNS
4. 备选：核心交换机静态路由115.231.251.88/29→防火墙内网口 + AF端口映射开内网回流


## 策略讨论（16:47，决定升级路线）
现状：开发负责人想把责任踢回网络侧；源酱对全权改网络有顾虑（牵扯底层多、风险不确定），计划找老大说明情况。

Shiro的建议（已给出）：
1. **升级是对的**——剩余两个关键未知数（SD-WAN供应商答复、开发配合意愿）都不在源酱单干能解决的范围内。升级≠甩锅，是带根因报告要分工决定
2. **责任分析**：app写死公网URL下发给内网客户端=设计缺陷（开发的锅）；内网→自家WAN IP被引流绕死=网络反常（网络的锅）。两边都能修，协调问题上升
3. **风险矩阵**：查配置🟢零风险 / 引流排除🟢已做过 / 静态路由🟢低-中（只影响本来就是死的流量，可回滚）/ 防火墙NAT回流🟡中（动的是正在工作的规则，需备份+变更窗口）/ hairpin未验证⚠️
4. **三步打法**：①零风险侦查（确认引流配置真的存上没存上+找DNAT规则在哪台设备+看SD-WAN静态路由页）→ ②带话术找老大要分工 → ③并行等供应商+开发答复
5. **保底**：应用侧getHlsUrl按来源返回内网地址（已实锤100%可行）


## 访问路径实测 + 方案C评估（16:56）
**访问 cloud.wapsh.com 实测路径**（源酱提问触发）：
- 内网DNS无分流，直接解析139.224.196.113（与公网一致）
- tracert: 10.12.41.1 → 100.64.0.1 → 100.65.0.1 → 172.31.x = **走SD-WAN隧道+云端行为管理**
- 出口SNAT: **124.160.149.204（联通出口）**
- 结论：**用公网身份访问**，服务器完全看不到10.12.41.101，看到的是124.160.149.204；内网身份在出公司前被替换；HTTP明文→云端审计全程可读
- ⭐关键推论：**方案A可行性再+1**——后端凭来源IP=124.160.149.204即可识别内网用户并返回172.16.0.210流地址（需做成可配置IP列表，出口IP可能变）

**方案C（静态路由+AF回流）影响评估**：
- 网络层：静态路由只影响115.231.251.88/29共8个IP的路径，**这批流量当前100%不通（80/443/83/554全灭）→ 零回归风险**，回滚=删路由秒级；顺带修复内网→该段其他已发布服务（当前也是死的）
- 安全面：**不新增暴露面**——目标172.16.0.210:83内网本就直达（多次实测200），回流只是同一目的地多一条经防火墙的路；公网侧映射本来就存在在用
- 唯一真实风险点：动**正在服务公网视频**的端口映射规则 → 回流选项**按规则开、只开:83**，纪律=改前备份+低峰+改完双端验证（手机+内网）+秒回滚
- 审计：内网→自家媒体服务器不再绕云端（现在绕了也是死流量，无审计价值）
- **真实不确定性=引流模式**：SD-WAN是路由模式还是透明桥接、PBR匹配条件——决定静态路由加哪层、会不会被盖掉 → 侦查阶段只读确认
- 前置条件已验：10.12.2.1:18443 TCP=True
- 结论：**可做、影响可控**，风险集中在防火墙那一步，靠变更纪律压住


## 方案C执行手册（17:10 定稿，待执行）
**原理**：静态路由(具体路由)优先级高于默认路由 → 内网到115.231.251.88/29的包直接指向防火墙私网口(10.12.2.1)，**物理上绕过SD-WAN默认引流路径**，不再经过100.64.x隧道/云端/联通出口。这也是前两次引流排除失败后的替代思路——不依赖SD-WAN配置。
**拓扑确认**：网关10.12.41.1，MAC 00-08-E3（华为系OUI），telnet:23开/HTTP:80开/SSH:22关；tracert hop2=100.64.0.1（SD-WAN设备=默认路由下一跳，路由模式非透明桥接）→ 静态路由方案可行。

**执行步骤**：
- 阶段0（只读）：①目标机tracert第一跳=其网关 ②网关上 display ip routing-table 0.0.0.0 与 10.12.2.1（确认默认下一跳&到防火墙路径不走SD-WAN）③AF后台(https://10.12.2.1:18443)定位端口映射规则115.231.251.94:83→172.16.0.210:83，确认有无「允许内网通过外网地址访问/NAT回流」选项 ④备份：AF配置导出 + 交换机配置(switch-backup脚本或show run)
- 阶段1（防火墙）：端口映射规则勾选NAT回流 → 保存 → 🚦闸门：手机流量视频必须仍能播（公网回归），不行立刻回滚
- 阶段2（网关加路由）：H3C `ip route-static 115.231.251.88 29 10.12.2.1` / 华为同 / Cisco `ip route 115.231.251.88 255.255.255.248 10.12.2.1`；若目标机网关不是10.12.41.1则在真实网关同样加；可选核心10.12.20.1同加覆盖全内网
- 阶段3（Shiro验证）：tracert不再进100.64.x + TCP83=True + 新鲜token m3u8=200 + 网页视频播放 + 回归(tracert223.5.5.5仍走隧道/手机视频正常)
- **关键机制提醒**：回流需DNAT+SNAT成对（否则回包源IP不匹配TCP断）→ AF勾选项应自带；若无该选项则需补SNAT规则(源=内网段目的=115.231.251.94:83 转源=10.12.2.1)
- 回滚：路由 undo/no 一条命令秒回；防火墙取消勾选或导入备份
- 失败排查：AF会话表查115.231.251.94:83有无会话 → 有=到防火墙了查回流/NAT；无=路由没生效或被PBR盖


## 最终方案定稿：域名映射（10-14 09:40，领导拍板）
**领导方案 = Shiro清单里的方案D（域名+分线DNS），经零改动预演验证可行：**
- `curl --resolve video.wapsh.com:83:172.16.0.210` 模拟域名→内网媒体服务器完整拉流 → **HTTP 200 + 完整m3u8**（媒体服务器不校验Host头，跨域有 ACAO:* 不受影响）
- 内网路径已证直连不进隧道：tracert 10.12.41.1 → 172.16.0.210 仅2跳

**执行三步：**
1. 后端 `getHlsUrl` 返回地址从裸IP换成域名（大概率是配置项 mediaServer，改配置+重启即完成开发没做完的那一步）
2. 内网DNS(DC01)：显式 A 记录 `video.wapsh.com → 172.16.0.210`
   ⚠️**通配符陷阱（实测）**：内网DNS已有 `*.wapsh.com → 10.11.10.10` 兜底（asdkfjtest等随机名全解析到DC），不加显式记录会解析到域控、故障极隐晦

## getHlsUrl为何返回裸IP——机制澄清（10-14 09:25，源酱提问）
